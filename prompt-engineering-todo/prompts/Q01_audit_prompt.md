# Запрос Q01: Аудит требований и карты процесса (Отдельный чат)
Версия: 1.0
Тип чата: Отдельный независимый чат аудита

## Текст промпта для отправки модели:

Ты выступаешь в роли ведущего системного архитектора и эксперта по качеству процессов разработки ПО.

### ЦЕЛЬ
Провести критический аудит представленных требований (R01–R10) и карты процесса работы с языковой моделью (Шаги A–F). Найти логические пропуски, противоречия, нестыковки передачи входов/выходов и оценить надежность возвратов при дефектах.

### ВХОДНЫЕ ДАННЫЕ

1. ТРЕБОВАНИЯ К ПРОГРАММЕ (TodoListApp.java, Java 17, 50-150 строк, без package, стандартная библиотека):
- R01: Файл TodoListApp.java, без package, Java 17, стандартная библиотека, 50-150 строк кода.
- R02: Задача: ID (1..N), текст, статус [ ] или [X]. При удалении задачи происходит непрерывная перенумерация оставшихся с 1 до текущего N.
- R03: `add <текст>` -> создает задачу, вывод `ADDED <id>`. При пустом тексте -> `ERROR: EMPTY_TASK`.
- R04: `list` -> выводит строки `<id>. [ ] <текст>` / `<id>. [X] <текст>`. Если список пуст -> `EMPTY`.
- R05: `done <id>` -> перевод в выполненные, вывод `DONE <id>`. Если уже была выполнена -> `ALREADY_DONE <id>`.
- R06: `remove <id>` -> удаление задачи, вывод `REMOVED <id>`. Оставшиеся задачи перенумеровываются от 1 до N.
- R07: Некорректный ID в `done`/`remove`: если не натуральное число -> `ERROR: INVALID_ID`; если id < 1 или id > N -> `ERROR: NOT_FOUND`.
- R08: Пустые строки ввода игнорируются. Неизвестная команда -> `ERROR: UNKNOWN_COMMAND`.
- R09: Завершение работы: команда `exit` (вывод `BYE`) или EOF.
- R10: Никаких приветствий, промптов приглашения ввода (`> `); строго одна строка ответа на каждое действие.

2. КАРТА ПРОЦЕССА:
- Шаг A: Аудит и согласование схемы (Вход: R01-R10, карта; Выход: замечания; КТ1: Человек принимает/отклоняет).
- Шаг B: Генерация сценариев тестов (Вход: согласованные R01-R10; Выход: таблица >=8 сценариев с граничными случаями; КТ2: Человек проверяет полноту покрытия).
- Шаг C: Генерация кода TodoListApp.java (Вход: R01-R10, тесты, ограничения Java 17; Выход: код и команды; КТ3: Человек компилирует javac и проверяет 50-150 строк).
- Шаг D: Прогон тестов (Вход: код, сценарии; Выход: логи запусков; КТ4: Человек сравнивает ожидание и факт. При успехе -> Шаг F; при сбое -> условный Шаг E).
- Шаг E [Условный]: Исправление дефекта (Вход: сбойный метод, симптом сбоя, Rxx; Выход: локальная правка; КТ5: Человек повторяет упавший тест, лимит 2 попытки; возврат к Шагу D).
- Шаг F: Подведение итогов и приёмка (Вход: финальный код, матрица, все логи; Выход: акт приёмки; КТ6: Человек принимает решение).

### ДЕЙСТВИЕ
Проанализируй требования и карту процесса. Для каждого замечания заполни структуру:
1. Затронутый шаг или требование.
2. Конкретный пропуск, неоднозначность или противоречие.
3. Последствие для реализации или тестирования.
4. Минимальное рекомендуемое исправление.

Отдельно проверь:
- Неразрывность цепочки «выход шага X -> вход шага Y».
- Полноту контрольных точек и корректность возврата при обнаружении дефекта (КТ4 -> Шаг E -> Шаг D).
- Не упущены ли граничные случаи в требованиях.

### ОГРАНИЧЕНИЯ
- Код программы НЕ пиши.
- Не добавляй новых тяжелых функций (сохранение на диск, дедлайны и т.д. запрещены границами учебной версии).
- Если данных недостаточно, сформулируй уточняющие вопросы человеку.

### ВЫХОДНОЙ ФОРМАТ
1. Таблица замечаний (Колонка 1: Шаг/Требование, Колонка 2: Проблема и последствия, Колонка 3: Минимальное исправление).
2. Оценка контрольных точек и схемы возврата.
3. Список открытых вопросов (если есть).
4. Общий вердикт о готовности карты (Готова / Требует точечных правок / Не готова).
