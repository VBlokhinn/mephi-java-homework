# Запрос Q02: Генерация тестовых сценариев и матрицы покрытия
Версия: 1.0
Чат: Основной рабочий чат Gemini

## Текст отправленного промпта:

Привет! Мы начинаем разработку консольного приложения «Список дел в памяти» на Java 17. Сейчас наш первый рабочий шаг - подготовить тестовые сценарии до написания кода.

Цель:
Сформировать полный набор тестовых сценариев и матрицу покрытия для проверки требований к программе.

Входные данные (актуальные требования v1.1):
1. R01: Программа в файле TodoListApp.java, без package, Java 17, UTF-8, стандартная библиотека, от 50 до 150 строк кода.
2. R02: Задача имеет номер от 1 до N, текст и статус не выполнена [ ] или выполнена [X]. При удалении задачи номера оставшихся сдвигаются (список всегда идет от 1 до текущего количества N).
3. R03: Команда add <текст> создает задачу с текстом (крайние пробелы текста обрезаются). При успехе выводит ADDED <номер>. При пустом тексте или только из пробелов выводит ERROR: EMPTY_TASK.
4. R04: Команда list выводит задачи построчно в формате номер, статус, текст (например, 1. [ ] Купить хлеб). Если задач нет, выводит ровно строку EMPTY.
5. R05: Команда done <номер> отмечает задачу выполненной и выводит DONE <номер>. Если уже выполнена - выводит ALREADY_DONE <номер>.
6. R06: Команда remove <номер> удаляет задачу, выводит REMOVED <номер> и перенумеровывает оставшиеся.
7. R07: В done и remove: если номер не натуральное число или отсутствует - выводит ERROR: INVALID_ID. Если номер меньше 1 или больше текущего N - выводит ERROR: NOT_FOUND.
8. R08: Команды строчные, чувствительны к регистру. Пустые строки игнорируются. На неизвестную команду или лишние аргументы у list/exit выводит ERROR: UNKNOWN_COMMAND.
9. R09: По команде exit выводит BYE и завершает работу. При закрытии потока ввода (EOF) завершает работу без вывода текста.
10. R10: Никаких приветствий и приглашений ввода. Строго одна строка ответа на каждое действие (кроме команды list, которая выводит по одной строке на каждую задачу).

Что нужно сделать:
Составь не менее 10 различных сценариев проверки. Среди них обязательно должно быть не менее 3 граничных случаев (например, пустой список, удаление единственной задачи, некорректные границы номеров). Для каждого сценария заранее определи точный ожидаемый вывод программы построчно.

Ограничения:
Код программы на этом шаге не пиши. Не меняй требования и не придумывай новые правила.

Формат ответа:
1. Таблица сценариев со столбцами:
- ID сценария (T01, T02 и так далее)
- Проверяемые требования (например, R03, R07)
- Тип сценария (позитивный, негативный или граничный с указанием конкретной границы)
- Последовательность входных команд (каждая команда с новой строки)
- Точный ожидаемый вывод программы (построчно, в точности как напечатает программа)
2. Матрица покрытия: для каждого требования от R01 до R10 укажи номера покрывающих его сценариев. Требования R01 и R10 пометь как проверяемые компиляцией и просмотром кода.

Критерий успешности:
Каждое требование покрыто хотя бы одним тестом, границы четко выделены, ожидаемый вывод полностью совпадает с правилами v1.1.

Действия при неопределенности:
Если какой-то сценарий невозможно однозначно вывести из требований, не выбирай поведение наугад, а задай уточняющий вопрос.
