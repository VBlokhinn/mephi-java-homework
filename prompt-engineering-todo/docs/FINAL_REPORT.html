2. Постановка задачи и критерии завершения

2.1. Спецификация требований R01–R10 (версия 1.1)

  • R01: Программа находится в файле TodoListApp.java, не содержит объявления package, компилируется и запускается на Java 17 в кодировке UTF-8, используя только стандартную библиотеку. Объём кода - от 50 до 150 строк.
  • R02: Модель задачи включает натуральный ID (1..N), текст и статус. При удалении задачи происходит непрерывная перенумерация оставшихся с 1 до текущего количества.
  • R03: add <текст> создает задачу. Пробелы по краям текста обрезаются (trim()). При пустом тексте выводится ERROR: EMPTY_TASK. При успехе выводится ADDED .
  • R04: list выводит нумерованный список задач построчно в формате . [ ] <текст> или . [X] <текст>. Если список пуст, выводится ровно строка EMPTY.
  • R05: done отмечает задачу выполненной, выводит DONE . Если уже выполнена - выводит ALREADY_DONE .
  • R06: remove удаляет задачу, выводит REMOVED , перенумеровывает оставшиеся.
  • R07: Если номер в done/remove не число или отсутствует - выводится ERROR: INVALID_ID. Если номер меньше 1 или больше текущего количества - ERROR: NOT_FOUND.
  • R08: Команды строчные, чувствительны к регистру. Пустые строки (и строки из одних пробелов) игнорируются. Неизвестные команды и лишние аргументы у list/exit вызывают ERROR: UNKNOWN_COMMAND.
  • R09: Команда exit выводит BYE и немедленно завершает работу. Конец потока (EOF) завершает программу молча (без вывода BYE).
  • R10: Отсутствуют приглашения ввода (> ). Каждому действию соответствует строго одна строка ответа, кроме команды list, выводящей по строке на задачу.

2.2. Критерии завершения (зафиксированы до начала работы)

1. Код компилируется на Java 17.

2. Код укладывается в 50–150 строк.

3. Проведено не менее 8 сценариев (включая не менее 3 граничных).

4. Требования R01–R10 покрыты в матрице прослеживаемости.

5. Разобран минимум 1 дефект (лимит до 2 попыток исправления).

6. Оформлен журнал, сохранен handoff-пакет, составлен акт приёмки.

9. Рефлексия (5–8 предложений)

В ходе выполнения проекта наиболее показательной частью предварительный аудит карты процесса в отдельной сессии языковой модели. На этом этапе было вскрыто скрытое логическое противоречие между требованием R10 ("строго одна строка ответа на каждое действие") и поведением команды list (R04), выводящей список построчно. Разрешение этой неопределённости до начала кодинга позволило избежать ошибок при подготовке сценариев проверки и написании кода. Работа с контрактами промптов, содержащими 7 обязательных элементов, доказала свою эффективность: модель с первой попытки сгенерировала рабочий код в 106 строк, точно уложившись в заданный диапазон 50–150 строк. Опыт локализации и устранения дефекта D01 продемонстрировал важность тестирования строгих неравенств. В будущих проектах можно использовать независимый аудит спецификаций до начала реализации, так как это экономит до 70% времени на отладку и, соответственно, токены.
